Create an editor component. The editor is responsible for displaying and editting journal entry content.

See [editor-props.tsx](./editor-props.tsx) for the props interface.

Blocks and spans both carry a stable `id`. IDs may be provided by the calling code, or generated by the editor itself when the editor creates new nodes. All tracking inside the editor — mapping blocks to BlockNote block ids, identifying which span a hover/apply event refers to, reconciling external content updates, etc. — is done by id. Because identity travels with the id rather than with the object reference, calling code is free to treat blocks and spans as immutable values: when state changes, produce a new block/span with the same id and updated fields.

When a user focuses on a block, the span content of the block should be displayed as plain text with no highlights. This should not be represented in the data model and is instead a view-only thing. The block should be marked as active while it's being editted.

If a user unfocuses from a block, the block should be marked as pending. Calling code will be notified and request corrections from the server. The editor should reduce the opacity of a pending block. While it's pending, the opacity should animate from 0.35 to 0.85 and back down over 3s.

If the user refocuses on a block, the block should be marked as active again. The timestamp is used to track when the block was last focused so stale corrections can be ignored.

When a correction is received, the calling code should replace the block's spans with a new array of spans (each with its own externally-provided id). These spans might have additional mistake highlights that weren't present in the original spans. This is because when a mistake in a parent span is fixed, mistakes in child subspans might be revealed.

The editor receives the nested format described in [corrections.ts](../../../model/corrections.ts).

Use SCSS for styling. Install necessary packages if needed for this.

# Functionality

User input should be limited as follows:

1. Only paragraphs are allowed.
2. No user-specified formatting.
3. No nested blocks.
4. No block options (any Notion-like block options should be hidden)
5. Disable any slash commands or hints for them.
6. Disable spell checking.
7. Disable autocomplete.

# IMPORTANT

- When the user selects a block, it INVALIDATES all mistakes in the block. When the user deselects, the block may be rechecked. this may occur even if no text has changed.

The following sitautions will never occur:

- Inserting text in the middle of a mistake span

# Styling

Use a light, minimal theme.

The editor is expected to be approximately centered in the page.

Blocks should be separated by a large gap so it's clear they're different units.

Active blocks are highlighted to show they are selected.

Blocks that are pending corrections have a spinner to the side of the block. Install the appropriate packages/icons for this.

The editor should have an easily readable width.

Pick a good font.

Editor should be padded on the left and right.

A left-hand gutter should contain a paragraph number and have space for the spinner. Multiple spinners can be active on different blocks. While the spinner is active, the block should have reduced opacity and no highlight.

Block highlights should expand into the gutter.

The selection box of the active block should not have borders.

The icon space for the gutter can also contain a warning icon if the block has a mistake or a checkmark icon if the block has no mistakes.

The spinner should be colorful and not a grey spinner.

When editting a block, use an arrow pointing right.

Both the gutter icons and the paragraph numbers should be the same size as the text.
